# Bingo 运营后台产品文档

C 端产品模型已完成,本仓库解决**运营后台的用户管理(M2)、活动管理(M4,仅兑换码)、
财务管理(M5)、账号管理(M6)、代理管理(M7)与系统设置(M8,仅风控参数)**。
在现有 `bingo-backend/apps/admin-api`(NestJS + GraphQL + Prisma)上**扩建**,不另起炉灶。

## 范围

**在范围内**:M2 用户管理、M4 活动管理(仅兑换码)、M5 财务管理、M6 账号管理、M7 代理管理
与 M8 系统设置(仅风控参数)的需求文档,以及写这些文档的规范。M6 同时是全平台权限模型的唯一定义方。

**不在范围内**:其余模块(数据中心、玩法)、活动管理中兑换码以外的活动、系统设置中未收入的页面
(RTP 取值范围、数值配置、下载记录)与代理域中尚未收入的渠道管理,
文档不由本仓库承载;
设计交付物(Figma 变量、组件库、设计交接)与竞品调研底稿同样不由本仓库承载。
文档只回答「要什么」,不回答「长什么样」。

需求会引用范围外的能力(活动彩金倍数、有效投注判定、站内信等)——
这些以业务名称出现,标注「本仓库范围外」,不指向本仓库内的路径。

> **财务于 2026-08 收入本仓库**(此前声明为「永久移出」)。理由:资金语义的唯一出处
> `资金模型.md` 在本仓库,而财务页面正是它被消费的地方 —— 拆两个仓库,R6–R17 的引用立刻断链。
> 收入范围后,`资金模型.md` 里把钱包、账变流水、打码任务等标注为「本仓库范围外」的说法已同步修正。

> **代理于 2026-08 收入本仓库**(M7,首版仅一级代理返佣)。理由同上:返佣的判档、打码与冲回
> 全部踩在资金语义上,文档必须与 `资金模型.md`、`标准计价.md` 同仓演进。
> 渠道管理与玩家端代理中心仍在范围外。

> **系统设置于 2026-08 部分收入本仓库**(M8,首版仅 8.1 风控参数一页)。理由:同IP/同设备
> 统计窗口是 M2 用户详情「风控数据」计数的唯一口径出处,注册多号限制是 M7 防刷佣的配套防线 ——
> 配置与消费方拆仓即断链。RTP 取值范围与系统设置其余页面仍在范围外。

> **活动(运营)于 2026-08 按活动逐页收入本仓库**(M4,首版仅 4.1 兑换码管理)。理由:活动奖励的
> 入账、随机金额、打码要求与领取门槛全部踩在资金语义上(彩金、打码任务、有效投注、标准计价),
> 文档必须与 `资金模型.md`、`标准计价.md` 同仓演进 —— 与财务、代理同理。运营活动种类极多,
> **不一次性全收**,逐个活动登记后另开需求;兑换码以外的活动与玩家端领取页仍在范围外。

## 目录结构

```
├── 00-公共约定/
│   ├── README.md            文档规范 + 数据归属规则 + 字段命名约定
│   ├── 页面模板.md            页面 README 的 v3 骨架,新建页面从这里复制
│   └── 校验.py              CI 校验脚本
├── M2-用户管理/
│   ├── README.md            模块契约:定位/术语/依赖/数据模型/页面索引/权限点/决策清单
│   └── <编号>-<页面名>/       只有已开工的页面才建文件夹
│       ├── README.md        页面需求文档
│       ├── <子视图>.md       (可选)拆出的辅助文件
│       └── 截图/             (可选)引用到的界面截图
├── M4-活动管理/              结构同上;首版仅 4.1 兑换码管理
├── M5-财务管理/              结构同上
├── M6-账号管理/              结构同上;权限模型是 6.2 的辅助文件
├── M7-代理管理/              结构同上;首版仅 7.1 代理返佣
├── M8-系统设置/              结构同上;首版仅 8.1 风控参数
└── .github/workflows/       CI
```

**核心规则:文件夹 = 页面。** 严格两层(模块 / 页面),菜单分组只在模块 README 的树里表达。
**有内容才建文件夹** —— 未开工的页面只存在于模块 README 的页面索引表,不建空占位目录。

## 文档规范

完整规范见 `00-公共约定/README.md`,要点:

1. **文档进 repo,跟代码同 PR 改。** 字段/规则变了不更新文档的 PR 视为未完成。
2. **不写页面布局。** 只回答"要什么"(字段、行为、状态),不回答"长什么样"——那是 Figma 的职责。
3. **不使用 emoji。** 状态用文字(`已有`/`改造`/`新增`),强调用加粗。
4. **不写待探讨。** 需求文档陈述决策;未定处写成明确假设,阻塞项统一记在模块 README 的决策清单。
5. **人日守恒**:需求人日之和 == 模块页面索引的人日。
6. **规则数值放配置,不放文档。** 文档只记:有哪些规则、语义、在哪配、谁能改。
