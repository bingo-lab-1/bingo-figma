# M5 · 财务管理

## 1. 定位与边界

**做什么**:玩家资金的进出与配置。**钱包余额、账变流水、打码任务、各类订单的唯一写入方。**

**不做什么**
- 不定义资金语义本身 —— 钱包与余额模型、真金彩金的地位、打码任务与核销、提现门槛,
  唯一出处是 `../M2-会员管理/2.1-会员列表/资金模型.md`,本模块**消费**它,不重复定义
- 不保留独立的「交易记录」查询页面 —— 它与 M2 的「账变记录」查询同一份账变流水,
  唯一运营查询入口固定为 M2.2 `/admin/users/wallet`;本模块继续拥有底层账本数据,但不重复提供界面
- 不做玩家档案管理(封禁、打标、调级归 M2)
- 其他活动规则由各活动维护；本模块 5.5 拥有充值赠送规则和运营商充值通用倍数。规则选择由充值赠送业务服务编排，底层钱包与账变只消费金额、倍数及来源，不反向查询活动配置
- [4.15 首充破产补助](../M4-活动管理/4.15-首充破产补助/README.md)在专用充值受理前提供宝箱资格及不可变活动依据；M5 建单锁定翻倍用途并排除仅本单的商品固定/比例彩金，不占比例次数。充值按 X 建码，补助由活动手动领取，钱包不反查活动配置（M4-D90）
- 不做通道对接的技术实现(只定义运营侧要什么配置与什么结果)
- 当前资金出入口为链上入金与链上提现:法币收单与代付均未接入,玩家法币充值和提现不能下单

**铁律**
- **无流水不得改余额**(资金模型 R7)。任何一次余额变化都要有账变流水,不允许静默改数
- 人工干预资金(人工充值、人工扣款、补单、人工生成订单、触发回调)**必须**二次确认 +
  原因必填 + 留痕,并进对账的重点关注项(资金模型 R15)
- **倍数缺失不等于 0 倍**。缺失一律拒绝入账,绝不退化成 0 倍放行(资金模型 FE20)

## 2. 术语表

> 资金类通用术语(钱包、余额、可兑换余额、真金、彩金、打码任务、有效投注、核销)
> **统一定义在 `../M2-会员管理/2.1-会员列表/资金模型.md` 第 2 段**,此处不重复。
> 下表只列本模块特有词,以及界面用词到资金模型术语的对照。

| 术语 | 定义 | 对照 |
|---|---|---|
| 轨 | 单一余额之下的资金来源分线。**真金轨**记充值来源,**彩金轨**记活动发放来源 | 资金模型 R16「两轨」 |
| Cash | 界面用词,即**真金轨**的入账 | = 真金 |
| JCoin | 界面用词,即**彩金轨**的入账 | = 彩金 |
| 商品 | 一个可售充值档位：面值、售价、到账真金、常规固定赠送及共享比例方案引用 | 5.5 |
| 充值通用倍数 X | 运营商所有真实充值采用的打码倍数，默认 1、正数，随订单/入金记录锁定 | 5.5 配置，资金模型 F1 消费 |
| 限次赠送方案 | 共享第 1～N 次比例、金额门槛、周期及彩金倍数，次数按成功比例奖励推进 | 5.5 |
| 首充补助翻倍订单 | 玩家在 4.15 主动选择后创建并绑定宝箱的专用商品订单；本单不发商品彩金、不占比例次数，真实支付成功只达成翻倍充值条件，补助另行手动领取 | 4.15 / 5.2 / 5.5，M4-D90 |
| 商品模板 | 一组商品的归类,套餐通过它引用商品 | 本模块拥有 |
| 套餐 | 支付方式与商品模板的绑定关系,决定玩家在某支付方式下看到哪些档位 | 本模块拥有 |
| 补单 | 支付成功但订单未变成功态时,人工把订单补成成功并完成入账 | 5.2 |
| 人工生成订单 | 不经玩家支付,由运营直接建一笔充值订单 | 入口在 5.5 商品预览,规则见 5.2 |
| 首充 | 该玩家第一笔充值,活动会用到 | 5.2 |

**两轨不是两个余额。** 单钱包单余额(资金模型 R6)保持不变,真金与彩金是这一个余额之下的
两条来源轨。凡界面上出现「真金金额 / 彩金金额」成对的列或输入框,一律是两轨的拆分或入账,
**不是两个可加减的余额** —— 全模块统一这一个说法,不再引入第三种叫法。

**只读引用**:用户、用户标签(owner=M2)· **VIP等级与逐级每日出款上限**(owner=M4,展示、风控参考及 D65 出款受理前校验)·
有效投注及其他活动彩金倍数(owner=各活动/玩法)· 支付方式(owner=通道能力,本模块只读引用其标识和可用状态,不据此登记独立页面)。

**4.17 资金衔接与验收边界**:同一轮完整彩金仅成功入账一次,重试始终查询并恢复原轮原领取记录,不得生成第二笔彩金或第二条打码任务。M4 在截止前已受理的领取可跨截止继续查证原结果;入账结果未知时保留处理中,不能当成失败换号重发,不能因轮次刷新撤回已入账彩金。彩金和独立打码任务按同一领取依据完成,缺失倍数或币种不可用按原资金异常规则处理。退款/冲正事实供活动重新核对未领取资格,不由财务自动推断活动应追回多少彩金。邀请机会、金额进度、轮次及其失效只在 M4 维护;本活动不新增充值订单用途例外,不改变 5.5 充值本金 X 或固定/比例赠送,也不占其赠送次数。4.16 奖励、7.1 佣金与既有打码任务各按原规则执行;投注加速统计读取玩法的最终结算有效投注,财务不另建一套有效投注算法。

**4.18 资金衔接与验收边界**:同一榜单、期间及玩家的奖励只成功入账一次,日榜和周榜可分别发奖并各建任务。未领取资格、可分配奖池、空缺份额及精度尾差不是资金支出;“实际发放奖金”仅合计真实成功的彩金账变。受理后金额、币种、Y及来源固定,未知结果查原申请,到期和关榜不取消在途履约。定榜后投注修正由活动受控核查,资金按既有纠错处理,不由财务自动推算新的名次、扣回彩金或清除任务;原始下注排名也不改写其他业务的有效投注规则。

> 数据结构由开发依据需求自行设计,本仓库只声明归属与读写边界。

**关于扣款为什么必须独立成节点**:D10 决定用方向下拉区分充值与扣款后,
若不给扣款单独的节点,则任何能人工充值的人都能扣款 —— 两个方向对玩家的影响相反,
风险也不对称,合并授权等于把扣款的门槛降到充值的水平。

**关于「提交审查」**:权限树没有该节点,提现订单页面也没有对应按钮,

(多选必填,挂在账号上不在角色上),定义见 M6 第 6 段。
本模块各页的列表、汇总与导出**一律先按该范围过滤再返回**。

**引用的外部权限节点**(owner=M2,在 M2 模块 README 汇总,此处不重复声明):
`user:detail:view` —— 本模块多页提供「点用户ID 进玩家详情」的跳出,受该权限约束。

**留痕分两类**:平台操作日志(账号管理 → 操作日志)由各业务写入,记录操作者、模块、动作、对象与前后值,
充值配置、赠送方案、人工商品单和恢复结算写入这里;提现的提交、分流、审核、放款和玩家取消
写入提现订单的只增动作记录。
