# 00-公共约定 · 跨模块规则与文档规范

> 本目录只放**真正无主的东西**(跨模块枚举、规范)。
> **所有业务表必须归属某个模块**,不许往这里堆 —— 这里变成垃圾桶,模块边界就没了。

---

# 一、文档结构规范

## 核心规则:**文件夹 = 页面**

```
bingo-figma/
├── M2-用户管理/                  ← 模块 = 一级菜单项(不是页面)
│   ├── README.md                模块契约
│   ├── 表设计.prisma
│   ├── 2.1-用户列表/README.md    ← 页面 = 一个路由
│   └── 2.2-钱包账变/README.md    ← 页面
```

**严格两层:模块 / 页面。没有第三层文件夹。**

- **分组不是页面,不建文件夹** —— 菜单分组只在模块 README 的「菜单结构」用树表达。
  这样菜单层级调整(嫌深就拍平)不用动文件系统。
- **页面判定标准**:能否被单独收藏/分享 URL。能 → 独立页面;不能 → 页面内 tab(写在所属页面 README 里)。
- **每个页面都建文件夹**,不分优先级 —— 否则模块的真实规模在文件系统上不可见。
  P0 写完整 9 段;P1/P2 可先写精简版,排期时补全。

## 两种 README,职责严格分开

| | 模块 README | 页面 README |
|---|---|---|
| 代表 | 一级菜单项 | 一个路由页 |
| 回答 | 管什么、依赖谁、有哪些表和页面 | 这一页长什么样、有哪些字段和操作 |
| 消费者 | 架构 / 后端 / 排期 | 设计(Figma) / 前端 / 测试 |
| 禁止 | 写具体页面怎么做 | 重复模块级的依赖和表定义 |

### 模块 README 模板(7 段)
```
frontmatter: module / name / owner / status / pages / p0 / estimate_days / updated
1. 定位与边界      做什么 + **不做什么** + 铁律
2. 术语表          本模块领域词汇,防词汇漂移
3. 依赖关系        上游(我引用) / 下游(谁引用我)
4. 数据模型        拥有的表 / 只读引用 → 表设计.prisma
5. 菜单结构与页面索引   分组树 + 页面表
6. 权限点汇总      M7 生成 RBAC seed 用
```

### 页面 README 模板 v3(11 段)
```
frontmatter: page / route / module / priority / status / estimate_days / spec_version / updated
1.  背景与目标        目标 + 背景 + 价值 + 不做什么 + **适用范围**
2.  入口              菜单位置 + 从哪些页面跳入
3.  术语              本页特有词(通用词引模块术语表)
4.  字段清单          字段 + 类型 + **可输入数据/校验规则**
5.  需求清单          索引:ID/需求/**触发条件**/验收/现状/权限/人日
6.  需求详述          复杂需求展开 7 栏
7.  数据流向与系统串接 输入→处理→显示 + 第三方对接
8.  异常与边界        正、反流程都想一遍(≥3 条)
9.  状态清单          声明必须存在哪些状态
10. 涉及表与职责      表归属 + 前后端职责
11. 关联页面
```

`spec_version: 3` 标记已迁移;缺此字段的页面按旧规则校验,不阻断 CI。

#### 1 · 适用范围(自检案例的教训)
必须写清 **终端 / 响应式断点 / 界面语言 / 时区 / 货币**。
不写,工程师就得来问"这是 APP 还是网页""要不要 RWD""哪个语言"。

#### 5 · 需求清单 —— 索引层
| ID | 需求 | 触发条件 | 验收标准 | 现状 | 权限码 | 人日 |

**触发条件**必填:按钮点击 / 键盘操作 / URL 直入 / 定时任务 / 外部回调。

#### 6 · 需求详述 —— 规格层,7 栏
**人日 ≥ 1,或涉及资金、权限、外部系统的需求,必须展开。** 其余在第 5 段一行即可。

| 栏位 | 内容 |
|---|---|
| 触发条件 | 详列触发行为 |
| 可输入数据 | 允许的类型、格式、长度、上下限 |
| 功能范围 | **前端做什么 / 后端做什么**,责任分明 |
| 处理逻辑 | 步骤式(1.2.3.),不用连续文字 |
| 错误处理 | 常见错误状况与对应提示 |
| 测试案例 | **正向与逆向各至少一例** |

#### 7 · 数据流向与系统串接
- **数据流向**:标明从用户端输入 → 后端处理 → 最终显示的完整路径,以及写入点与缓存策略
- **系统串接**:涉及第三方(支付通道、游戏厂商、推送、对象存储)时,列明**对接人、正向与逆向流程、每个环节的责任边界**——避免模糊空间

**不写页面结构/区块布局/组件摆放。** 那是 Figma 的职责,写在这里会与设计稿分叉。
本文档只回答**要什么**(字段、行为、状态),不回答**长什么样**(位置、尺寸、样式)。

**不使用 emoji。** 需求文档靠结构和措辞表达轻重,不靠图标。状态与优先级用文字(`已有`/`改造`/`新增`,`P0`/`P1`/`P2`),强调用加粗。CI 会检查。

#### 1. 背景与目标 —— 说清"为什么"
目标(一句话可度量)· 背景(现状痛点与已有基础)· 价值(在全局中的位置)· **不做什么**(边界,防蔓延)。
避免"模糊描述或天花乱坠",用条列式,不用大段连续文字。

#### 5. 异常与边界 —— 反流程
| # | 场景 | 触发条件 | 预期处理 |

**与「状态清单」的区别**:状态清单是 **UI 呈现态**(空/加载/错误);异常与边界是 **业务反流程**(越权、并发、超限、脏数据、幂等)。
每条应能对应一个测试用例。**少于 3 条视为没想过反流程。**

#### 8. 涉及表与职责
除表归属外,必须标明**前后端职责**:校验、权限、脱敏、异步任务归谁。
"权限只在前端判"这类问题,写清职责表就能在评审时被抓出来。

#### 4. 需求清单 —— 规格的核心

| ID | 需求 | 验收标准 | 现状 | 权限码 | 人日 |
|---|---|---|---|---|---|
| 3.2-R4 | 单条审核通过 | 二次确认 → 状态转 `paying` → 写 `OperationLog` | 新增 | `finance:withdraw:review` | 1 |

**规则**
1. **原子性**:一条需求 = 一个可独立验收的行为 = 大致一个 PR。拆不动为止。
2. **编号**:`<页面号>-R<n>`,如 `3.2-R4`。编号是稳定标识,**不复用、不重排**。
3. **验收标准可证伪**:写"点击 X → 发生 Y",不写"体验良好""功能完善"。
4. **现状**必填,取值 `已有`(仅适配)/ `改造`(有基础需改)/ `新增`(从零)。
   区分已有与新增,开发才知道哪些是改造;**人日按现状差异估**。
5. **人日守恒**:`sum(需求人日) == frontmatter.estimate_days`。校验脚本会检查。
6. 权限码写在需求行上 —— 模块 README 第 6 段的权限点汇总由此聚合。

> 需求清单直接转 issue 和测试用例。**转不了的,说明还没拆到位。**

### 关于「待探讨」
**页面和模块 README 不写待探讨。** 需求文档陈述决策,不罗列疑问。
- 未定的地方 → 在需求行里写成**明确假设**(如"按 FIFO 处理"),错了再改
- 真正阻塞的跨模块决策 → 统一记在 `01-模块总览.md` 的决策清单,**唯一一处**

## 前端导航约定(已定)
- **经典单列可折叠侧边栏**(非两列图标栏)
- **不做多标签工作区** —— 单页面视图,不保留已打开页面的 tab 条
- 路由深度与菜单层级一致,如 `/financial/withdrawal/order`

## 状态与优先级图例
现状:`已有` · `基本可用` · `需改造` · `大缺口` · `缺失`
优先级:`P0` = MVP 必须 · `P1` = 首个迭代 · `P2` = 后续
需求行的「现状」列只取三值:`已有` / `改造` / `新增`

# 二、跨模块引用规则

## ① 表的归属:谁写它,谁拥有它

| 表 | owner | 理由 |
|---|---|---|
| `User` `UserTag` `VipLevel` | M2 | 注册/封禁/打标是 M2 的写操作 |
| `Wallet` `Transaction` `*Order` | M3 | 充值/提现/账变是 M3 的写操作 |
| `Activity` `ActivityClaim` | M4 | 活动配置与发放 |
| `Agent` `Channel` | M5 | 代理与渠道维护 |

读不需要所有权。**所有业务表必须有 owner 模块。**

## ② 引用只声明,不重复定义
引用方 `表设计.prisma` 顶部列出外部表 + owner,字段上标 `FK →`。
**禁止把同一张表抄进两个模块** —— 必然分叉。

## ③ 每个模块 README 必须写双向依赖
- `上游依赖`:我引用了谁
- `下游被依赖`:谁引用我 ← **改表前先看这行**

## ④ 依赖方向铁律
1. **`M3 财务` 不得反向依赖 `M4 活动`** —— 资金域只认账变,活动信息以**元数据 ID** 传入(见 `WagerRequirement.sourceId`,不建外键)
2. **`M1 报表` 只读汇总表**,禁止直连业务表
3. **`M7 权限/日志` 横切所有模块**,M3/M4 的写操作必须留痕

# 三、字段与命名约定

## 金额
- 加密货币 `Decimal(20, 8)` · 法币 `Decimal(20, 2)`
- **禁止用 String/Float 存金额**(竞品 ETL 用 Text 存,是反面教材)
- 余额四分账:`balance`(真金)· `bonusBalance`(彩金)· `frozenBalance`(冻结)· 打码进度单独建表

## 字段分三层(混写是文档腐烂头号原因)
- **L1 实体字段** —— 落库的事实
- **L2 枚举字典** —— 受控值,独立版本化
- **L3 派生指标** —— 只读视图,**必须写明公式 + 时区 + 数据源**

## 权限码
格式 `模块:对象:动作`,如 `user:list:view` `user:ban` `finance:withdraw:review`
每个页面 README 声明自己的权限码,模块 README 汇总,M7 据此生成 seed。
