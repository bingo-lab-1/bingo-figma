# 00-公共约定 · 文档规范与数据归属规则

> 本目录只放**真正无主的东西**:写文档的规范、命名约定、校验脚本。
> **所有业务内容必须归属某个模块**,不许往这里堆 —— 这里变成垃圾桶,边界就没了。

**机械规则由 `校验.py` 检查**:冲突标记、认可的模板结构、标题、需求编号、链接和流程图代码块。语义正确性与可读性仍需人工审查。
本文只写校验器测不了的东西:判断标准、为什么、以及约定本身。
写页面时按用途选择下表中的模板。

# 一、文档结构与写作规范

## 目录保持稳定

目录仍采用“模块 / 页面”。一个独立页面对应一个编号目录,页面正文放在 README.md。菜单分组不建目录。模块索引保留已有正文;尚无正文的独立页面,仅在已核实侧边栏存在入口时登记,不为不存在的菜单保留空页面名。

活动的参与、领取和发放记录在对应活动内部查询,字段、权限、操作和验收随父页面正文维护,不另编独立记录页编号,也不另列侧边栏菜单。多个活动可以复用查询组件,数据归属和业务口径仍由各活动负责。已有独立入口及正文不因这项整理一并取消。

保留已有目录、需求编号和决策编号。移除空登记不重排其他页面编号,也不将原编号挪给其他功能,避免旧引用指向错误内容。

内容较长的子视图或共用说明可放同目录辅助文件,不再建子目录;图片放“截图/”,名称说明内容并由文档引用。模块的活动清单、共用规则导航直接放在模块目录,由模块 README 链接,不算独立页面。

页面直接从“编号 · 名称”标题和业务介绍开始,不再附元信息表。路由、优先级、负责人和状态在Jira维护,修改记录由Git保存。辅助文件和导航也按此原则逐篇整理;校验器检查正文标题和结构。

## 文档与 Jira 分工

**PRD是确定的实施与验收依据。** 正文和决策表只写执行结论,不保留悬而未决的方案。每项规则写明触发条件、处理结果和异常行为;不在本版范围内的功能直接说明不提供。金额等运营配置须定义类型、范围、默认值或必填要求。任务管理信息只在Jira维护。

开发、测试、验收和发布进度只在 Jira 维护。页面相关资料可以链接 ticket,不复制它的当前状态。模块索引区分“已有文档 / 仅登记”,避免把文档编写情况叫作开发开工情况。工作量估算、排期及交付进度也在Jira维护。

## 按页面类型选择模板

页面统一使用六部分结构,按用途选择模板。模块README保持定位与边界、术语、依赖、数据归属、页面索引、权限和决策七部分;共用模型、辅助表单、技术方案及证据文档不套页面模板。

| 顺序 | [活动模板](页面模板.md) | [查询模板](查询页面模板.md) | [配置模板](配置页面模板.md) | [业务处理模板](业务处理页面模板.md) |
|---|---|---|---|---|
| 1 | 活动介绍 | 用途 | 用途 | 用途 |
| 2 | 运营配置 | 查询条件 | 配置项 | 查询与处理信息 |
| 3 | 参与和领奖规则 | 结果字段 | 操作规则 | 处理规则 |
| 4 | 特殊情况 | 操作规则 | 特殊情况 | 特殊情况 |
| 5 | 验收场景 | 验收场景 | 验收场景 | 验收场景 |
| 6 | 相关资料 | 相关资料 | 相关资料 | 相关资料 |

活动模板用于资格与奖励;查询模板用于以查数、详情和导出为主的页面;配置模板用于规则、账号、角色等维护;业务处理模板用于订单审核、资金操作、链上入金及关系处理。混合页面按主要业务选择,列表型配置页的筛选和展示字段写入配置项。

新建需求时先确定承载位置:已有活动内部的记录查询直接补入父页面;独立页面复制对应模板,填写真实标题与编号,在所属模块索引登记。正文必须替换全部占位符,每项需求都有编号和可执行验收场景。章节名称、顺序和数量按模板校验;小节按业务内容组织。校验不再接受十二段页面或旧六栏详述。

已迁移页面保留旧章节的隐藏锚点以兼容外部链接;新引用使用当前章节名称或A、R编号。旧格式只存在于Git历史,不作为新增需求的模板。

## 先把业务讲清楚

介绍先回答谁在用、要做什么、能得到什么。随后按实际操作顺序写,每句话尽量说清“谁、什么时候、做什么、结果是什么”。运营读正文不应需要不断跳转查编号。

- 写“用户在截止前提交领奖,系统尚未处理完,超过截止后仍继续处理这次申请”,少写“合法在途跨截止结算”。
- 写“本轮门槛和奖励保持不变,修改只影响新一轮”,少写“旧轮按快照履约”。
- 门槛、次数、金额含义必须清楚;举例标明“示例”,不要把示例金额当默认值。
- 允许简短总结和必要重复,但每条规则只指定一个主要维护位置,不要在多张表里维护相同默认值。
- 正文直接解释规则,编号用于追踪。已有 A 编号可随规则放在小节标题或表格中;已有 R 编号放在验收场景,不得删除或挪作其他需求。
- 内容只说当前规则。已失效内容由 Git 保存,不要用页首补丁覆盖整篇旧正文。

## 特殊情况也用业务语言

保留会影响用户权益或运营操作的边界:条件不足、漏领、中断、关闭活动、修改配置、重复操作、处理失败等。说明用户看到什么、原有奖励如何处理、是否允许重试。

规则变更时同步正文、验收场景、模块决策和所有引用方。决策表保留编号与结论,不复制讨论历史。跨模块规则指定一个主要维护位置并附链接。系统里的配置草稿、资金处理中和链上确认是业务状态,应写清进入、退出及异常处理,与文档成熟度无关。

需求约束与实现手段分开:PRD写不可重复发奖、资金结果必须可查询;具体表结构、接口、队列、签名服务等写在开发维护的技术设计中。现有辅助技术方案保留原路径,由关联页面链接访问。

界面字段、可执行操作、提示含义和状态属于PRD;区块摆放、颜色、组件样式交给Figma。空、加载、错误、无权限为公共必需状态,页面仅补充特殊表现。

## 验收与相关资料

每条需求都要能对应具体场景:给定什么条件、用户或运营做什么、预期发生什么。成功场景与不满足条件的场景都要覆盖。资金类需求还须覆盖重复请求和结果未知。

相关资料说明入口、权限、记录查询、共用规则与责任边界,并链接 Jira。服务端必须核对资格与权限,不能只靠界面隐藏按钮。涉及外部事实时写清归谁提供,不在活动中另造一套口径。

流程图只在比文字更容易理解时使用,纯查询页不强制画图。已有图随规则一起更新;分支图可标注正常、异常颜色含义,跨模块流程说明责任方。CI检查图的语法,人工检查图是否符合正文。

## 编号、历史与写作约束

决策编号D全仓唯一,新决策取现有最大号加一,模块内不重新起号。模块决策表记录决定和依据,规则细节链接正文。根README维护编号分配导航。

不使用装饰性emoji,不维护手工修订历史表,不在PRD画页面线框。Git保存历史,Figma维护设计。需求优先级仍为P0首次交付必需、P1首个迭代、P2后续。

# 二、数据归属与引用规则

本仓库现覆盖 M2 用户管理 · M4 活动管理 · M5 财务管理 · M6 账号管理 · M7 代理管理 · M8 系统设置。
这些模块的数据既被范围外的能力(资金账本、玩法、报表)读写,**模块之间也互相引用**。
**边界写不清,改一个字段就会在看不见的地方炸掉** —— 所以归属和依赖必须显式声明。

## ① 数据的归属:谁写它,谁拥有它

| 数据 | owner | 理由 |
|---|---|---|
| 用户 用户标签 实名认证 封禁记录 点控记录 | M2 | 注册/封禁/打标是 M2 的写操作 |
| VIP等级(等级序列、升降级门槛、保级与降级规则) | M4 | 等级配置与调级是 M4 的写操作;M2 与 M5 只读展示与筛选 |
| 活动配置、参与资格与发放依据(含各类签到) | M4 | 配置、资格和奖励依据由活动拥有,资金入账结果归M5 |
| 钱包 账变记录 财务订单与打码任务 | M5 | 财务拥有事实,活动触发并只读资金结果;底层语义唯一来源仍在M2资金模型 |
| 投注记录 | 范围外(玩法) | 只读展示 |
| 代理关系与佣金 | M7 | M7拥有绑定及返佣,邀请活动只读关系并独立判断有效客户 |
| 渠道字典 | 代理渠道能力(本仓库范围外) | 活动定向通过M2用户标签复用渠道属性 |

读不需要所有权。**所有业务数据必须有 owner,范围外的也要写明归谁。**

## ② 引用只声明,不重复定义

引用方在模块 README 第 4 段的「只读引用」里列出外部数据 + owner。
**禁止把同一份数据的定义抄进两处** —— 必然分叉。

## ③ 模块 README 必须写双向依赖

- `上游依赖`:我引用了谁
- `下游被依赖`:谁引用我 ← **改数据结构前先看这行**

范围外的依赖照写,标注「本仓库范围外」,不指向本仓库内的路径。

## ④ 依赖方向铁律

1. **资金域不得在账务链路上依赖活动域** —— 账变、打码与已经受理后的放款结算不得用活动数据重新计算金额,
   活动信息只以来源标识或判定快照传入,账本不反向关联活动配置。
   **两类只读消费不在此限**:一是展示与风控参考;二是玩家提交出款申请时,M5 可读取 M4 的受控属性
   「当前 VIP 等级 + 该级每日出款次数 / 金额上限」做受理前资格校验(D65),并把等级与上限固化到订单快照。
   这个例外只决定申请能否受理,不得改变钱包余额、账变金额或通道实际放款金额
2. **用户域与活动域** —— 活动域可读用户域(标签、玩家档案);用户域也可把活动域的
   **受控属性**用作条件(2.5 用 VIP 等级),前提是 **该属性的判定输入不得包含用户标签**。
   VIP 由充值与有效投注等原始数据判定、不读标签,依赖图因此单向:
   `原始数据 → VIP 等级 → 用户标签 → 活动门槛`。
   **「等级判定输入」与「奖励领取门槛」必须分开命名** —— 前者不许出现标签,后者可以;
   混称是这条铁律最可能被违反的方式
3. **报表只读汇总数据**,禁止直连业务数据
4. **权限与日志横切一切** —— 封禁、解封、调级、改账号等干预操作**必须**留痕。
   标签自 M2.5 起由规则判定,留痕对象是**规则的变更**;系统自动打标摘标另记进出流水

# 三、字段与命名约定

## 金额

- 加密货币小数 8 位 · 法币小数 2 位 · 汇率与中间计算至少 18 位
- **禁止用字符串或浮点存金额**(竞品用文本存,是反面教材)
- 金额一律**带币种标识**,不允许出现无币种的裸数字

> **资金语义不在这里定义。** 钱包与余额模型、真金彩金的地位、打码任务与核销、
> 提现门槛、跨币种闪兑与义务迁移,唯一出处是
> `M2-用户管理/2.1-用户列表/资金模型.md` —— 那是这些数字被消费的地方。
> 本节只留命名与精度这类无主的通用约定,**不得把语义抄第二份**。

## 字段分三层(混写是文档腐烂头号原因)

- **L1 实体字段** —— 落库的事实
- **L2 枚举字典** —— 受控值,独立版本化
- **L3 派生指标** —— 只读视图,**必须写明公式 + 时区 + 数据源**

## 权限码

格式 `模块:对象:动作`,如 `user:list:view` `user:ban` `user:tag:edit`
每个页面 README 声明自己的权限码,模块 README 汇总,权限模块据此生成 seed。

# 四、工具与完成标准

## 能自动生成的不手写

| 产物 | 工具 |
|---|---|
| API 契约 | `spectaql` / `graphql-markdown`,从 GraphQL schema 生成 |
| 流程图语法校验 | mermaid-cli,CI 逐张解析 |

**数据模型不在本仓库维护。** 文档只声明数据归属与读写边界(模块 README 第 4 段),
具体结构由开发依据需求自行设计 —— 文档里再存一份必然分叉。

## 完成的定义(DoD)

运营能独立讲清玩法,开发能确定行为边界,测试能从具体场景判断结果。每项规则都有明确结论,所有异常分支都有处理结果;格式检查通过不代替业务一致性审查。

## 现在不写的东西

| 项 | 原因 | 何时补 |
|---|---|---|
| API 契约文档 | 从 GraphQL 自动生成 | 页面需求定稿后 |
| 验收标准 Gherkin | 需求清单的验收标准已可转测试 | 功能定稿后逐个补 |
| RBAC 权限矩阵 | 代码里角色与权限已较完整 | 权限点收齐后 |

**有内容才建文件,不为"体系完整"预先占位。** 目录结构应是内容长出来的结果。
