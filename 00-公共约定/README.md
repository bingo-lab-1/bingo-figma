# 00-公共约定 · 跨模块规则与文档规范

> 本目录只放**真正无主的东西**(跨模块规范)。
> **所有业务数据必须归属某个模块**,不许往这里堆 —— 这里变成垃圾桶,模块边界就没了。

**机械规则由 `校验.py` 强制**(段落结构、必填栏位、编号一致性、emoji、适用范围维度)。
本文只写校验器测不了的东西:判断标准、为什么、以及约定本身。
写页面时用 `页面模板.md`,行内注释已在写作现场提示,本文不重复。

---

# 一、文档结构规范

## 核心规则:**文件夹 = 页面**

```
bingo-figma/
├── M2-用户管理/                  ← 模块 = 一级菜单项(不是页面)
│   ├── README.md                模块契约
│   └── 2.1-用户列表/README.md    ← 页面 = 一个路由
```

**严格两层:模块 / 页面。没有第三层文件夹。**

- **有内容才建文件夹。** 未开工的页面只存在于模块 README 的页面索引表 ——
  索引表是页面存在与否的唯一出处,不建空占位目录。开始写时再建。
  校验器只报「有文件夹但索引未列」(野文件夹),不报反向。
- **空的页面目录允许存在,但只在本地。** git 不跟踪空目录,所以它进不了远端,
  可以当作「这一页我要开工了」的个人标记。校验器对空的页面目录放行;
  其余位置的空目录仍报错 —— 那通常是误删残留。
- **分组不是页面,不建文件夹** —— 菜单分组只在模块 README 的「菜单结构」用树表达。
  这样菜单层级调整(嫌深就拍平)不用动文件系统。
- **页面判定标准**:能否被单独收藏/分享 URL。
  能 → 独立页面文件夹;不能但内容多 → 同文件夹下的辅助文件;不能且内容少 → 直接写在 README 里。

**辅助文件**:页面文件夹内可以有,但不得再建子文件夹。

```
2.1-用户列表/
├── README.md          页面本体(12 段)
├── 用户详情弹窗.md      辅助文件:内容量足以淹没页面本身的子视图
└── DESIGN.md          辅助文件:设计说明
```

拆出的判据是**内容量**(经验值:超过 README 三分之一)加**独立成篇更好读**。
拆出后 README 只留入口 + 索引 + 链接,不重复内容。
辅助文件带简化 frontmatter(`名称 / 所属页面 / 模块 / 优先级 / 状态 / 更新`),
段落自由编排 —— 它不是页面,不受 12 段模板约束。

## 两种 README,职责严格分开

| | 模块 README | 页面 README |
|---|---|---|
| 代表 | 一级菜单项 | 一个路由页 |
| 回答 | 管什么、依赖谁、有哪些数据和页面 | 这一页要什么字段、什么行为、什么状态 |
| 消费者 | 架构 / 后端 / 排期 | 设计(Figma) / 前端 / 测试 |
| 禁止 | 写具体页面怎么做 | 重复模块级的依赖和数据定义 |

**模块 README(7 段)**:定位与边界 · 术语表 · 依赖关系 · 数据模型 · 菜单结构与页面索引 · 权限点汇总

**页面 README v3(12 段)**:背景与目标 · 入口 · 术语 · 关键参数与假设 · 字段清单 ·
需求清单 · 需求详述 · 数据流向与系统串接 · 异常与边界 · 状态清单 · 涉及表与职责 · 关联页面

段落顺序与名称不可改 —— 校验器按完全匹配判定是否已迁移 v3,匹配即自动进入严格检查。

## 全文只写需求,不写技术怎么实现

**整份文档都不规定实现方式**,包括后半段。需求定的是必须达成什么,手段是开发的判断。

| 写这个(需求/约束) | 不写这个(实现方式) |
|---|---|
| 每次取数都要判权限 | 每个 tab 一个独立接口 |
| 导出不得阻塞页面 | 用队列还是 Worker |
| 拒绝并提示无权限 | 返回 403 |

技术名词换业务说法:接口→取数 · 前端→界面 · 后端→服务端 · HTTP 状态码→"提示无权限"。

> 判断标准:**换一套技术栈重写,这份文档还成不成立?** 成立才是需求,不成立就是设计。

## 读者分层:前半段所有人能读,后半段是技术规格

PRD 不能只有技术看得懂。运营、财务、老板都要能读懂这一页干什么、为什么值得做。

| 段落 | 主要读者 | 语言要求 |
|---|---|---|
| 1 背景与目标 | **所有人**(含老板) | 不出现代码、数据名、文件路径、接口名(校验器强制) |
| 2–6 入口至需求清单 | 运营 + 技术 | 业务语言,参数描述其影响 |
| 7–12 详述至关联页面 | 技术 + 测试 | 允许技术术语 |

**第 1 段写用户当前的痛,不写系统现状。**

> 反例:「现有用户列表已有基础筛选,但维度不足」
> 正例:「客服接到投诉要先找到人,现在得在多个页面来回跳,响应慢还容易查错人」

## 消灭重复性信息

同一个阈值散落在处理逻辑、异常表、流程图里,**改一处忘三处**是最常见的错误来源。

- **第 4 段「关键参数与假设」是所有数值的唯一出处**,编号 `A1` `A2`,其余段落和图一律写「见 A1」
- 每条标明是**已验证依据**还是**未验证假设** —— 假设要能被逐条挑战
- **规则数值放配置,不放文档。** 文档只记:有哪些规则、语义、在哪配、谁能改
- 第 6 段需求清单是**索引**,第 7 段需求详述是**规格**,同一栏位不在两处都写全
- frontmatter 只留 6 项。页面编号从文件夹名推导、人日归模块索引表、
  规范版本由段落结构本身判定 —— 能推导的一律不写

## 状态清单的全局默认

**空 / 加载 / 错误 / 无权限四态所有页面都必须有**,不必在每页重复声明。
第 10 段只写两类:**本页的表现差异**(错误是卡片级还是整页、加载是骨架屏还是转圈)、
**本页特有态**(数据未成熟、参数过大折叠、活动已下线仍显示历史)。

没有特有态、表现也无差异时,这一段写「四态按全局默认」即可 —— 不要抄一遍四态。

## 流程图规则

**一图解千言。** 不要写"用户下单后系统如何如何"的大段文字,画图。

| 情形 | 图型 | 放哪 |
|---|---|---|
| 有状态流转(订单、打码、冻结、封禁、结算) | `stateDiagram-v2` | 第 7 段需求详述内 |
| 处理逻辑有分支/循环 | `flowchart TD` | 第 7 段 或 第 8 段 |
| **跨模块或跨系统的交接** | `sequenceDiagram`(泳道) | **`01-模块总览.md`,不放单页** |
| 第三方对接 | `sequenceDiagram`,含正向与逆向 | 第 8 段系统串接 |

**什么时候不画**:纯查询/CRUD 页(报表、日志、简单列表)。为画而画只增加维护成本。

画法:方向自上而下 · 用颜色标出错误分支与安全关键步骤并在图下说明配色 ·
跨模块用泳道标明每个环节的责任方。语法由 CI 逐张解析,错误会渲染成红色报错框。

## 不写页面结构,不用 emoji

**不写区块布局/组件摆放。** 那是 Figma 的职责,写在这里必然与设计稿分叉。
Figma 稿在页面目录下以 `DESIGN.md` 链接过去。

**不使用 emoji。** 靠结构和措辞表达轻重,状态与优先级用文字,强调用加粗。校验器会查。

## 与业界 PRD 模板的两处有意偏离

参照 [PRD 怎麼寫](https://pagerank.ing/prd/) 与
[流程圖指南](https://pagerank.ing/beginner-product-manager-flowcharts-guide/)。
以下两项**是该模板要求、我们有意不做** —— 不是遗漏,不要"补上"。

- **不做修订追踪表。** `git log` 与 PR diff 就是修订史且不会忘记更新;
  手工维护的修订表必然滞后,滞后的比没有更危险。补偿:PR 描述里写清变更点。
- **不做页面线框图。** 所有视觉表达交给 Figma,文档里的线框与设计稿必然分叉。
  补偿:字段清单与状态清单写足,`DESIGN.md` 链到 Figma。

## 关于「待探讨」

**页面和模块 README 不写待探讨。** 需求文档陈述决策,不罗列疑问。

- 未定的地方 → 在需求行里写成**明确假设**(如"按 FIFO 处理"),错了再改
- 真正阻塞的跨模块决策 → 统一记在 `01-模块总览.md` 的决策清单,**唯一一处**

## 前端导航约定(已定)

- **经典单列可折叠侧边栏**(非两列图标栏)
- **不做多标签工作区** —— 单页面视图,不保留已打开页面的 tab 条
- 路由深度与菜单层级一致,如 `/financial/withdrawal/order`

## 状态与优先级图例

现状:`已有` · `基本可用` · `需改造` · `大缺口` · `缺失`
优先级:`P0` = MVP 必须 · `P1` = 首个迭代 · `P2` = 后续

# 二、跨模块引用规则

## ① 数据的归属:谁写它,谁拥有它

| 数据 | owner | 理由 |
|---|---|---|
| 用户 用户标签 VIP等级 | M2 | 注册/封禁/打标是 M2 的写操作 |
| 钱包 账变记录 各类订单 | M3 | 充值/提现/账变是 M3 的写操作 |
| 活动 活动领取记录 | M4 | 活动配置与发放 |
| 代理 渠道 | M5 | 代理与渠道维护 |

读不需要所有权。**所有业务数据必须有 owner 模块。**

## ② 引用只声明,不重复定义

引用方在模块 README 第 4 段的「只读引用」里列出外部数据 + owner。
**禁止把同一份数据的定义抄进两个模块** —— 必然分叉。

## ③ 每个模块 README 必须写双向依赖

- `上游依赖`:我引用了谁
- `下游被依赖`:谁引用我 ← **改数据结构前先看这行**

## ④ 依赖方向铁律

1. **`M3 财务` 不得反向依赖 `M4 活动`** —— 资金域只认账变,活动信息以**来源标识**传入,不与活动建立关联
2. **`M1 报表` 只读汇总数据**,禁止直连业务数据
3. **`M7 权限/日志` 横切所有模块**,M3/M4 的写操作必须留痕

# 三、字段与命名约定

## 金额

- 加密货币小数 8 位 · 法币小数 2 位
- **禁止用字符串或浮点存金额**(竞品用文本存,是反面教材)
- 余额分账记录:真金 · 彩金 · 冻结,三者分开;打码进度独立于余额单独记录
- **真金与彩金都需打码才能提现**:充值真金默认 1 倍(可配置),彩金随活动配置。打码要求覆盖两者

## 字段分三层(混写是文档腐烂头号原因)

- **L1 实体字段** —— 落库的事实
- **L2 枚举字典** —— 受控值,独立版本化
- **L3 派生指标** —— 只读视图,**必须写明公式 + 时区 + 数据源**

## 权限码

格式 `模块:对象:动作`,如 `user:list:view` `user:ban` `finance:withdraw:review`
每个页面 README 声明自己的权限码,模块 README 汇总,M7 据此生成 seed。

# 四、工具与完成标准

## 能自动生成的不手写

| 产物 | 工具 |
|---|---|
| API 契约 | `spectaql` / `graphql-markdown`,从 GraphQL schema 生成 |
| 流程图语法校验 | mermaid-cli,CI 逐张解析 |

**数据模型不在本仓库维护。** 文档只声明数据归属与读写边界(模块 README 第 4 段),
具体结构由开发依据需求自行设计 —— 文档里再存一份必然分叉。

## 完成的定义(DoD)

开发拿到文档后能直接转成 **数据结构变更 + issue + 测试用例**,
不用回来问"这个字段什么意思""这条规则阈值多少"。达不到即未完成。

## 现在不写的东西

| 项 | 原因 | 何时补 |
|---|---|---|
| API 契约文档 | 从 GraphQL 自动生成 | 02/03 稳定后 |
| 验收标准 Gherkin | 需求清单的验收标准已可转测试 | 功能定稿后逐个补 |
| RBAC 权限矩阵 | 代码里角色与权限已较完整 | 权限点收齐后 |
| 业务规则数值 | 缺带数据的实盘账号 | 拿到账号后 |

**有内容才建文件,不为"体系完整"预先占位。** 目录结构应是内容长出来的结果。
