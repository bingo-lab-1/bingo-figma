# 00-公共约定 · 跨模块规则与文档规范

> 本目录只放**真正无主的东西**(跨模块枚举、规范)。
> **所有业务表必须归属某个模块**,不许往这里堆 —— 这里变成垃圾桶,模块边界就没了。

---

# 一、文档结构规范

## 核心规则:**文件夹 = 页面**

```
bingo-figma/
├── M2-用户管理/                  ← 模块 = 一级菜单项(不是页面)
│   ├── README.md                模块契约
│   ├── 表设计.prisma
│   ├── 2.1-用户列表/README.md    ← 页面 = 一个路由
│   └── 2.2-钱包账变/README.md    ← 页面
```

**严格两层:模块 / 页面。没有第三层文件夹。**

- **分组不是页面,不建文件夹** —— 菜单分组只在模块 README 的「菜单结构」用树表达。
  这样菜单层级调整(嫌深就拍平)不用动文件系统。
- **页面判定标准**:能否被单独收藏/分享 URL。能 → 独立页面;不能 → 页面内 tab(写在所属页面 README 里)。
- **每个页面都建文件夹**,不分优先级 —— 否则模块的真实规模在文件系统上不可见。
  P0 写完整 12 段;P1/P2 可先写精简版,排期时补全。

## 两种 README,职责严格分开

| | 模块 README | 页面 README |
|---|---|---|
| 代表 | 一级菜单项 | 一个路由页 |
| 回答 | 管什么、依赖谁、有哪些表和页面 | 这一页长什么样、有哪些字段和操作 |
| 消费者 | 架构 / 后端 / 排期 | 设计(Figma) / 前端 / 测试 |
| 禁止 | 写具体页面怎么做 | 重复模块级的依赖和表定义 |

### 模块 README 模板(7 段)
```
frontmatter(中文键): 模块 / 名称 / 负责人 / 状态 / 更新
1. 定位与边界      做什么 + **不做什么** + 铁律
2. 术语表          本模块领域词汇,防词汇漂移
3. 依赖关系        上游(我引用) / 下游(谁引用我)
4. 数据模型        拥有的表 / 只读引用 → 表设计.prisma
5. 菜单结构与页面索引   分组树 + 页面表
6. 权限点汇总      M7 生成 RBAC seed 用
```

### 页面 README 模板 v3(12 段)
```
frontmatter(中文键): 名称 / 路由 / 模块 / 优先级 / 状态 / 更新
1.  背景与目标        目标 + 谁在用/用来做什么 + 业务价值 + 不做什么 + 适用范围
2.  入口              菜单位置 + 从哪些页面跳入
3.  术语              本页特有词(通用词引模块术语表)
4.  关键参数与假设    ★ 所有阈值的**唯一出处**,标明哪些是未验证假设
5.  字段清单          字段 + 类型 + 可输入数据/校验规则
6.  需求清单          索引:ID/需求/触发条件/验收标准/权限码
7.  需求详述          复杂需求展开 6 栏
8.  数据流向与系统串接 输入→处理→显示 + 第三方对接
9.  异常与边界        正、反流程都想一遍(≥3 条)
10. 状态清单          声明必须存在哪些状态
11. 涉及表与职责      表归属 + 前后端职责
12. 关联页面
```

#### 读者分层:前半段所有人能读,后半段是技术规格

PRD 不能只有技术看得懂。运营、财务、老板都要能读懂**这一页是干什么的、为什么值得做**。

| 段落 | 主要读者 | 语言要求 |
|---|---|---|
| **1 背景与目标** | **所有人**(含老板) | **不出现代码、表名、文件路径、接口名** |
| 2 入口 · 3 术语 | 所有人 | 术语用业务语言定义,不写代码标识 |
| 4 关键参数 · 5 字段清单 | 运营 + 技术 | 参数用业务语言描述其影响 |
| 6 需求清单 | 所有人 | 需求名与验收标准用业务语言 |
| 7–12 详述/流程/表/职责 | 技术 + 测试 | 允许技术术语 |

**第 1 段的三条硬规则**
1. **不写"现有实现在哪个文件"** —— 那是工程师才关心的;页面是否已有,
   frontmatter 的 `状态` 已经说明,散文里再说是重复
2. **写清"谁在用、用来做什么、没有会怎样"** —— 老板据此判断值不值得投人
3. **不写"现有不足"式的系统状态**,写**用户当前的痛** —— 前者是技术视角,后者才是需求来源

> 反例:「现有 `user.resolver` 已有基础列表,但筛选维度不足」
> 正例:「客服接到投诉要先找到人,现在得在多个页面来回跳,响应慢还容易查错人」

#### frontmatter 只留 6 项

```yaml
名称: 用户列表与详情
路由: /user/list
模块: M2
优先级: P0
状态: 已有
更新: 2026-07-27
```

**不写**能从别处推导的字段,理由与第 4 段「关键参数」一致——重复即分叉:

| 不写 | 从哪里得到 |
|---|---|
| 页面编号 | 文件夹名(`2.1-用户列表` → `2.1`) |
| 人日 | 模块 README 的页面索引表(唯一出处) |
| 规范版本 | **段落结构本身**——段落名匹配 v3 模板即为已迁移,比人工标记可靠 |

#### 4 · 关键参数与假设 —— 消灭重复性信息

同一个阈值(超时秒数、行数上限、有效期)散落在处理逻辑、异常表、流程图里,
**改一处忘三处**是需求文档最常见的错误来源,工程师会反复回来确认哪个是对的。

规则:
1. 所有数值集中在本表,编号 `A1` `A2` …,**本表是唯一出处**
2. 其余段落一律写「见 A1」,**不重复写数值**
3. 每条标明是**已验证依据**还是**未验证假设**——假设要能被逐条挑战
4. 图里同样引用编号,不写死数值

#### 两段之间不重复表述
第 6 段需求清单是**索引**(扫一眼知道有哪些需求、要什么权限),
第 7 段需求详述是**规格**(怎么实现)。触发条件在索引里写简写,在详述里写完整,
其余栏位不在索引重复。

#### 6 · 需求清单 —— 索引层
| ID | 需求 | 触发条件 | 验收标准 | 权限码 |

- **触发条件**必填:按钮点击 / 键盘操作 / URL 直入 / 定时任务 / 外部回调
- **不写人日和现状**——排期信息归模块 README 的页面索引表,
  需求文档面向所有读者,不掺排期口径
- 编号 `<页面号>-R<n>`,稳定标识,**不复用不重排**

#### 7 · 需求详述 —— 规格层,6 栏
**涉及资金、权限、外部系统,或处理逻辑有分支的需求必须展开。** 其余在第 6 段一行即可。

| 栏位 | 内容 |
|---|---|
| 触发条件 | 详列触发行为(比第 6 段索引更完整) |
| 可输入数据 | 允许的类型、格式、长度、上下限 |
| 功能范围 | **前端做什么 / 后端做什么**,责任分明 |
| 处理逻辑 | 步骤式(1.2.3.),不用连续文字 |
| 错误处理 | 常见错误状况与对应提示 |
| 测试案例 | **正向与逆向各至少一例** |

#### 流程图规则

**一图解千言。** 不要写"用户下单后系统如何如何"的大段文字,画图。

**什么时候必须画**

| 情形 | 图型 | 放哪 |
|---|---|---|
| 有状态流转(订单、打码、冻结、封禁、结算) | `stateDiagram-v2` | 页面第 7 段需求详述内 |
| 处理逻辑有分支/循环 | `flowchart TD` | 第 7 段需求详述 或 第 8 段数据流向 |
| **跨模块或跨系统的交接** | `sequenceDiagram`(泳道) | **`01-模块总览.md`,不放单页** |
| 第三方对接 | `sequenceDiagram`,含**正向与逆向** | 页面第 8 段系统串接 |

**什么时候不画**:纯查询/CRUD 页(报表、日志、简单列表)。为画而画只增加维护成本。

**画法**
- 方向自上而下(短流程可左右)
- **用颜色标出错误分支与安全关键步骤**,并在图下一行说明配色含义
- 跨模块用 `participant` 或 `subgraph` 当泳道,**标明每个环节的责任方**
- 先画简单版跑通,再加条件分支和循环;画完找人对一遍

**渲染**:GitHub 原生渲染 ` ```mermaid ` 代码块。VS Code 需装 Mermaid 预览插件。
**语法错误会渲染成红色报错框**,比没有图更糟——CI 会校验语法。

#### 8 · 数据流向与系统串接
- **数据流向**:标明从用户端输入 → 后端处理 → 最终显示的完整路径,以及写入点与缓存策略
- **系统串接**:涉及第三方(支付通道、游戏厂商、推送、对象存储)时,列明**对接人、正向与逆向流程、每个环节的责任边界**——避免模糊空间

**不写页面结构/区块布局/组件摆放。** 那是 Figma 的职责,写在这里会与设计稿分叉。
本文档只回答**要什么**(字段、行为、状态),不回答**长什么样**(位置、尺寸、样式)。

**不使用 emoji。** 需求文档靠结构和措辞表达轻重,不靠图标。状态与优先级用文字(`已有`/`改造`/`新增`,`P0`/`P1`/`P2`),强调用加粗。CI 会检查。

#### 1 · 背景与目标 —— 说清"为什么"
目标(一句话可度量)· 谁在用/用来做什么/没有会怎样 · 业务价值 · **不做什么**(边界,防蔓延)。
避免"模糊描述或天花乱坠",用条列式,不用大段连续文字。

**适用范围**(自检案例的教训)
必须写清 **终端 / 响应式断点 / 界面语言 / 时区 / 货币**。
不写,工程师就得来问"这是 APP 还是网页""要不要 RWD""哪个语言"。

#### 9 · 异常与边界 —— 反流程
| # | 场景 | 触发条件 | 预期处理 |

**与「状态清单」的区别**:状态清单是 **UI 呈现态**(空/加载/错误);异常与边界是 **业务反流程**(越权、并发、超限、脏数据、幂等)。
每条应能对应一个测试用例。**少于 3 条视为没想过反流程。**

#### 11 · 涉及表与职责
除表归属外,必须标明**前后端职责**:校验、权限、脱敏、异步任务归谁。
"权限只在前端判"这类问题,写清职责表就能在评审时被抓出来。

### 与业界 PRD 模板的两处有意偏离

本规范主要参照 [PRD 怎麼寫](https://pagerank.ing/prd/) 与
[流程圖指南](https://pagerank.ing/beginner-product-manager-flowcharts-guide/)。
以下两项**是该模板要求、我们有意不做**——不是遗漏,不要"补上"。

#### 一、不做修订追踪表

原模板要求文档开头放一张「修订追踪表」(改了什么 / 改在哪 / 什么时候)。

**不做的理由**
- 本仓库是 docs-as-code,`git log` / PR diff 就是修订史,且**不会忘记更新**
- 手工维护的修订表必然滞后于内容,滞后的修订表比没有更危险
- frontmatter 的 `updated` 已标注最后变更日期

**代价与补偿**:不看 git 的读者(设计、运营、管理层)拿不到"这次改了什么"。
补偿方式是**在 PR 描述里写清变更点**,并在评审会上口头过一遍——
原模板设这张表的目的本就是让团队知情,PR + 评审能达成同样目的。

#### 二、不做页面线框图(wireframe)

原模板第六段是「頁面設計(wireframe)」,要求低保真骨架图。

**不做的理由**
- 我们把**所有视觉与布局表达**交给 Figma,文档只回答"要什么"不回答"长什么样"
- 文档里的线框与 Figma 稿必然分叉,分叉后没人知道哪个是准的
- 原模板反对的是"手伸進設計師的飯碗"(视觉设计),我们把这条**执行得更严格**

**代价与补偿**:读文档时脑子里没有画面。
补偿方式是页面 README 的**字段清单 + 状态清单**足够完整,
Figma 稿在页面目录下以 `DESIGN.md` 链接过去,两者一一对应。

### 关于「待探讨」
**页面和模块 README 不写待探讨。** 需求文档陈述决策,不罗列疑问。
- 未定的地方 → 在需求行里写成**明确假设**(如"按 FIFO 处理"),错了再改
- 真正阻塞的跨模块决策 → 统一记在 `01-模块总览.md` 的决策清单,**唯一一处**

## 前端导航约定(已定)
- **经典单列可折叠侧边栏**(非两列图标栏)
- **不做多标签工作区** —— 单页面视图,不保留已打开页面的 tab 条
- 路由深度与菜单层级一致,如 `/financial/withdrawal/order`

## 状态与优先级图例
现状:`已有` · `基本可用` · `需改造` · `大缺口` · `缺失`
优先级:`P0` = MVP 必须 · `P1` = 首个迭代 · `P2` = 后续

# 二、跨模块引用规则

## ① 表的归属:谁写它,谁拥有它

| 表 | owner | 理由 |
|---|---|---|
| `User` `UserTag` `VipLevel` | M2 | 注册/封禁/打标是 M2 的写操作 |
| `Wallet` `Transaction` `*Order` | M3 | 充值/提现/账变是 M3 的写操作 |
| `Activity` `ActivityClaim` | M4 | 活动配置与发放 |
| `Agent` `Channel` | M5 | 代理与渠道维护 |

读不需要所有权。**所有业务表必须有 owner 模块。**

## ② 引用只声明,不重复定义
引用方 `表设计.prisma` 顶部列出外部表 + owner,字段上标 `FK →`。
**禁止把同一张表抄进两个模块** —— 必然分叉。

## ③ 每个模块 README 必须写双向依赖
- `上游依赖`:我引用了谁
- `下游被依赖`:谁引用我 ← **改表前先看这行**

## ④ 依赖方向铁律
1. **`M3 财务` 不得反向依赖 `M4 活动`** —— 资金域只认账变,活动信息以**元数据 ID** 传入(见 `WagerRequirement.sourceId`,不建外键)
2. **`M1 报表` 只读汇总表**,禁止直连业务表
3. **`M7 权限/日志` 横切所有模块**,M3/M4 的写操作必须留痕

# 三、字段与命名约定

## 金额
- 加密货币 `Decimal(20, 8)` · 法币 `Decimal(20, 2)`
- **禁止用 String/Float 存金额**(竞品 ETL 用 Text 存,是反面教材)
- 余额四分账:`balance`(真金)· `bonusBalance`(彩金)· `frozenBalance`(冻结)· 打码进度单独建表

## 字段分三层(混写是文档腐烂头号原因)
- **L1 实体字段** —— 落库的事实
- **L2 枚举字典** —— 受控值,独立版本化
- **L3 派生指标** —— 只读视图,**必须写明公式 + 时区 + 数据源**

## 权限码
格式 `模块:对象:动作`,如 `user:list:view` `user:ban` `finance:withdraw:review`
每个页面 README 声明自己的权限码,模块 README 汇总,M7 据此生成 seed。

# 四、工具与完成标准

## 能自动生成的不手写
| 产物 | 工具 | 说明 |
|---|---|---|
| ERD | `prisma-erd-generator` | 从 `表设计.prisma` 生成,不手画 |
| 数据字典 | `prisma-docs-generator` | 注释即文档 |
| API 契约 | `spectaql` / `graphql-markdown` | 从 GraphQL schema 生成 |
| 流程图 | mermaid(手写)+ CI 语法校验 | 逻辑需人判断,但语法机器管 |

手写的必然与代码分叉。**CI 应校验 schema 变更与文档同步。**

## 完成的定义(DoD)
开发拿到文档后能直接转成 **schema diff + issue + 测试用例**,
不用回来问"这个字段什么意思""这条规则阈值多少"。达不到即未完成。

## 现在不写的东西(避免提前铺目录)
| 项 | 原因 | 何时补 |
|---|---|---|
| API 契约文档 | 从 GraphQL 自动生成 | 02/03 稳定后 |
| 验收标准 Gherkin | 需求清单的验收标准已可转测试 | 功能定稿后逐个补 |
| RBAC 权限矩阵 | 代码里 `Role/Permission` 已较完整 | 权限点收齐后 |
| 业务规则数值 | 缺带数据的实盘账号 | 拿到账号后 |

**有内容才建文件,不为"体系完整"预先占位。** 目录结构应是内容长出来的结果。
