# 4.6 · VIP配置

## 1. 背景与目标

**目标**:让运营自己定“充多少、投多少能升级,每个完整保级周期要完成多少有效投注,
未完成时降到哪一级,每一级每周每月能拿多少钱、什么时候能领,每天最多能申请几次出款、累计最多能出多少钱”。
玩家能看到自己离下一级还差多少,并获得与等级匹配的持续回馈和出款权益。

**谁在用**

| 角色 | 用来做什么 | 没有会怎样 |
|---|---|---|
| 运营 | 定等级门槛与保级要求、定三类奖励和逐级出款上限、通过用户标签圈定参与人群、开关活动 | 想调一档等级的权益要找程序员改代码,调完还不敢确认改对没有 |
| 玩家 | 知道自己在第几级、离下一级差多少、每周每月能领多少、当天还能出款几次和多少钱 | 只看到一个等级数字,不知道它值多少钱,也不知道为什么不能继续出款 |
| 财务 / 风控 | 看这套等级体系每月发出去多少钱,并在玩家申请出款时执行该等级的每日次数与金额上限 | 长期奖励成本和出款额度说不清楚,异常资金流出也缺少统一闸口 |

**业务价值**:等级把"充值 + 下注"两件事绑在一起,只做一样升不上去;
周月两档持续回馈给玩家一个固定的回访理由,不像一次性活动打完就散;
保级流水让高等级的待遇需要持续活跃来维持,成本不会一路只涨;
每一级每一类奖励的金额、门槛、领取窗口与每日出款上限都在同一张页面上,改一个数不用动代码。

**不做什么**

- **不做玩家端的等级页和进度条** —— 这里只是后台,玩家看到的另外做
- **不做加钱和打码本身** —— 这里只定规则和触发,真正加钱、记打码由资金那边管
- **不做玩家端出款申请、审核和放款** —— 本页只配置每个 VIP 等级的每日出款次数与金额上限;申请受理、额度占用、审核、放款和额度释放由 M5 财务域负责
- **不做人群怎么算** —— 注册天数、累计充值、登录设备数、注册渠道等条件全部由用户标签计算,本页只选标签
- **不做发放记录页** —— 谁在什么时候领了多少在「VIP 奖励发放记录」里看,本页只放入口
- **本页不做签到奖励** —— 原始表里签到也按等级分档,现独立在 [4.10 签到奖励](../4.10-签到奖励/README.md)起草;本页只提供等级,不承载签到配置
- **不做升级奖励** —— 原始表有这一项,本轮的三类奖励里没有,见决策 D62
- **不做单个玩家手工调级** —— 等级平时只由规则判定,后台不提供“把某个玩家直接设成 VIP5”的入口;等级归档前的批量迁移除外
- **不做多套模板** —— 一个运营商一套配置,不做 A/B 或多版本并存

**适用范围**

| 维度 | 取值 |
|---|---|
| 终端 | 电脑后台,按 1440px 宽设计 |
| 响应式 | 最小支持 1280px;不做手机版 |
| 界面语言 | 后台用简体中文;活动名称与等级名按运营语言填(线上为葡语) |
| 时区 | 所有领取窗口、保级结算的自然日与自然月一律按业务时区切;界面展示时间按运营所在时区(GMT−3)并标注 |
| 货币 | 两套口径,互不换算:**升级门槛、保级流水与领取全额奖励所需本月累计充值按平台标准计价币种判定**,与用户标签里的金额同一把尺子;**奖励金额与入账按活动自己选的奖励币种**。一个运营商一套配置 |

## 3. 术语

> 通用词(打码倍数、领取门槛)见 `../README.md` 第 2 段;彩金、打码任务、有效投注
> 见 `../../M2-用户管理/2.1-用户列表/资金模型.md`;标签、命中、重算见
> `../../M2-用户管理/2.5-用户标签/README.md` 第 3 段,这里不重复讲。

| 术语 | 定义 |
|---|---|
| 等级序号 | 等级的身份与排序依据,正整数,**一经使用永不复用**(D58);归档后的号永久保留且不再用于新等级,序列因此可能不连续 |
| 等级名 | 展示用的名字,可以是「1」「2」也可以是「黄金」「白金」;**只用于显示,不参与任何判定与排序** |
| 升级门槛 | 一个等级的准入线,由充值金额与投注金额两项组成,**两项都达到才升**(D57) |
| 保级周期 | 从玩家升入当前等级的时刻起算一个完整日历月;保级成功后,下一周期紧接上一周期开始 |
| 保级流水 | 维持当前等级在一个完整保级周期内要完成的有效投注量;周期结束时没做够,就按「未完成降级」处理 |
| 未完成降级 | 保级没达成时降到哪一级,**填等级序号**,不填"降几级" —— 序列可能不连续,"降一级"没有确定含义 |
| 周奖励 / 月奖励 | 按等级配的固定金额,每周 / 每月开一次领取窗口,玩家在窗口内手动领 |
| 投注返现奖励 | 按等级配的返现,以上一自然日的有效投注为基数,次日开窗口手动领 |
| 领取窗口 | 一段允许领取的时间;错过不补,不累积到下一期 |
| 当日最高出款次数 | 玩家在一个业务自然日内最多可被系统受理的出款申请笔数;受理时先占 1 次,拒绝、取消或放款失败后释放 |
| 当日最高出款金额 | 玩家在一个业务自然日内最多可被系统受理的出款申请总额;按申请金额、即手续费前的总额累计,统一换算为平台标准计价币种 |
| 出款额度占用 | 系统受理申请时原子占用本日次数与金额,防止玩家并发提交多笔申请绕过上限;最终成功则转为已使用,失败则释放 |

## 7. 需求详述

### 4.6-R1

**触发条件**:页面加载时读出当前配置;运营改动任意字段后点右侧悬浮「保存」。

**可输入数据**:见第 5 段「基础设置」八项;数值类只收数字,时刻类只收 24 小时制。

**功能范围**

| 归属 | 做什么 |
|---|---|
| 界面 | 表单交互、即时格式提示、改奖励币种时弹二次确认、保存前把未填必填项标红 |
| 服务端 | 整份校验后才落库,部分通过不落;权限判定;用户标签按当前已启用的清单校验 |

**处理逻辑**

1. 加载:读出基础设置、等级序列与每级三张奖励表,一次性给全,不分段取。
2. 运营改动;界面只做格式提示,不做业务判定。
3. 点保存 → 服务端按 A1 ~ A24 整份校验(等级、奖励与出款限制的校验见 R2 / R3 / R7)。
4. 全部通过才落库;落库后立即生效 —— 配置改动不设延迟,与 4.4-A13 同口径。
5. 刷新页面显示;开关与纯文案的改动同样立即生效。

**错误处理**

| 错误状况 | 提示 |
|---|---|
| 活动名称为空或超长 | 活动名称必填,长度 1 ~ 40 |
| 打码倍数 ≤ 0 | 打码倍数必须大于 0 |
| 领取窗口起止时刻颠倒 | 结束时刻不能早于开始时刻 |
| 奖励币种未选 | 请先选择奖励币种,奖励金额需要它才有意义 |
| 选中的标签已被停用或删除 | 标签「X」已不可用,请重新选择 |
| 没有权限 | 没有操作权限(服务端也会拦,不靠藏按钮) |

**测试案例**

- 正向:填齐八项、打码 3 倍、周窗口改成周五 10:00 ~ 22:00 → 保存成功,重进页面数据一致。
- 逆向:活动名称留空 + 打码倍数填 0 → 一次性列出两条错误,都定位到具体字段,不落库。

### 4.6-R2

**触发条件**:点「新增等级」「启用 / 停用」「迁移玩家」「归档」;改任一门槛或保级流水后点保存。

**可输入数据**:序号(正整数,系统给,不可手填)· 等级名(1 ~ 20 字符)· 充值金额与投注金额
(非负数)· 保级流水(非负数)· 未完成降级(下拉选已存在且启用的更低序号,可留空)·
当日最高出款次数(≥ 0 的整数)· 当日最高出款金额(≥ 0、最多 2 位小数的标准计价币种金额)。

**功能范围**

| 归属 | 做什么 |
|---|---|
| 界面 | 行内编辑、新增行、迁移预览与二次确认、归档前二次确认、「未完成降级」与迁移目标下拉只列合法的更低序号 |
| 服务端 | 序号与名称唯一性、升级与出款门槛校验、迁移目标及人数校验、批量迁移留痕、归档前非空检查 |

**处理逻辑**

1. 新增:序号取历史最大值加一,**不填补空洞**(A9、D58);新增行默认停用,填完再启用。
2. 校验序号与名称:序号唯一,已归档的号不得重新出现;等级名去掉首尾空格并忽略大小写后,不可与现有或本次新增的其他等级重名。例如「Gold」与「 gold 」视为同名。
3. 校验门槛:序号越大,充值金额与投注金额**都不得低于**前一个启用等级 —— 否则会出现"升到高级反而门槛更低"。
4. 校验保级流水:非负数;不强制单调。
5. 校验未完成降级:填的序号必须存在、启用、且小于本级序号;留空表示不降级。
6. 校验出款上限:次数必须为整数,金额最多 2 位小数,两项均不得为负且不得留空。任一项为 0 都代表该等级当日不可出款;界面必须给出醒目提示并在保存前二次确认。
7. 停用:不拦,但提示该级当前玩家数;停用后新玩家不能升入,原有玩家在迁移完成前保持该等级,并继续按该级配置领取奖励和执行该级出款上限。
8. 迁移:只允许把停用等级中的玩家迁往一个**已存在、已启用且序号更低**的等级。执行前展示来源等级、目标等级、影响人数与“不补发、不追回历史奖励、不撤销已受理出款”的说明,运营二次确认后服务端批量执行。
9. 迁移留痕:逐个玩家记录原等级、目标等级、时间、操作人和原因「等级归档迁移」;迁移完成时以该时刻为新等级的保级周期起点,给予一个完整日历月。迁移后的新出款申请按目标等级上限判断,当天既有成功与占用额度继续计入。
10. 归档:该等级玩家数为 0 时才允许;归档后不再出现在日常配置与升级候选中,但序号、名称和历史记录永久保留,序号不得复用。
11. 全部通过才落库;等级序列的任何改动都会影响 4.2 红包雨的金额档覆盖校验(4.2-A6),保存后给一条提示。

**错误处理**

| 错误状况 | 提示 |
|---|---|
| 高等级的门槛低于低等级 | 第 N 级的充值 / 投注门槛不能低于第 M 级 |
| 等级名称重复 | VIP等级名称「X」已存在,请使用其他名称 |
| 未完成降级填了不存在或已停用的序号 | 第 N 级的降级目标「X」不存在或已停用,请重选 |
| 未完成降级填了不小于本级的序号 | 降级目标必须低于当前等级 |
| 出款次数不是整数或小于 0 | 当日最高出款次数必须是大于或等于 0 的整数 |
| 出款金额小于 0 或超过 2 位小数 | 当日最高出款金额不能为负数,且最多保留 2 位小数 |
| 出款上限任一项为 0 | 该等级将无法出款,确认仍要保存吗 |
| 迁移目标不合法 | 迁移目标必须是已启用且低于当前等级的等级 |
| 归档时该等级还有玩家 | 第 N 级还有 X 名玩家,请先迁移后再归档 |
| 序号试图复用 | 序号 X 已归档,不能再次使用 |
| 一个等级都没有 | 至少要有一个启用的等级 |

**测试案例**

- 正向:VIP1 配当日最高出款 1 次、20 USD → 保存成功,重进数据一致;停用 VIP4 并把 120 名玩家迁移到 VIP2 → 玩家开始新的完整保级周期,后续申请按 VIP2 出款上限判断。
- 逆向:VIP3 仍有玩家时直接归档 → 拦下并提示玩家数;新建名称同为「黄金」的等级 → 拦下;把 VIP3 的充值门槛改到低于 VIP2 → 拦下,整份不落库。

### 4.6-R3

**触发条件**:展开某个等级的奖励区;改动三张表的任一格;点保存。

**可输入数据**:奖励金额(周 / 月为非负金额,返现为 0 ~ 100 的比例)· 领取全额奖励所需本月累计充值
(非负金额)· 未达标时的免费领取百分比(0 ~ 99 的整数)。

**功能范围**

| 归属 | 做什么 |
|---|---|
| 界面 | 三张表可折叠;明确提示「本月充值达标领全额,未达标按免费比例领取」 |
| 服务端 | 校验本月累计充值门槛与免费比例,领取时按 A15 计算实际比例和金额 |

**处理逻辑**

1. 每个等级各有三张表:周奖励、月奖励、投注返现奖励,结构相同(A14)。
2. 本月累计充值达到「领取全额奖励所需本月累计充值」时,发放该类奖励的 100%。
3. 未达到门槛(包括完全未充值)时,只能发放「原奖励 × 免费领取百分比」;免费比例配置为 0% 时不发。
4. 三张表允许留空 —— 留空表示该级不发这一类奖励,不是校验错误。
5. 新增等级时三张表默认全空。
6. 免费部分按奖励币种的最小单位舍入,舍入方式沿用钱包入账规则;计算结果为 0 时不创建账变与打码任务。
7. 全部通过才落库;已发出去的奖励不受影响(A20)。

**错误处理**

| 错误状况 | 提示 |
|---|---|
| 返现比例超出 0 ~ 100 | 返现比例必须在 0 到 100 之间 |
| 免费领取百分比超出 0 ~ 99 | 免费领取百分比必须在 0 到 99 之间;只有本月充值达标才能领取 100% |
| 填了奖励金额但没选奖励币种 | 请先在基础设置里选择奖励币种 |
| 金额为负 | 金额不能为负数 |

**测试案例**

- 正向:VIP3 周奖励填 50、本月累计充值门槛填 100、免费比例填 20% → 本月累计充值 80 的玩家领 10,累计充值 100 的玩家领 50。
- 逆向:返现比例填 150 或免费比例填 120 → 拦下,整份配置不落库。

### 4.6-R4

**触发条件**:玩家充值到账时、投注结算时(升级判定);每个玩家自己的保级周期到期时(保级与降级判定)。无后台按钮。

**可输入数据**:无人工输入;判定的输入只有玩家的累计充值金额与累计有效投注,
以及本次完整保级周期内的有效投注 —— **不含任何用户标签**(00-公共约定 铁律④第 2 款)。

**功能范围**

| 归属 | 做什么 |
|---|---|
| 界面 | 无。等级变动的结果在 2.1 用户列表与详情弹窗里看 |
| 服务端 | 判定、写等级、记升降级流水;活动关闭时不判定 |

**处理逻辑**

1. 升级:每次充值到账或投注结算后,取该玩家的累计充值金额与累计有效投注,
   与**下一个启用等级**的两项门槛比对;**两项都达到才升**(A10、D57)。
2. 一次可跨多级:同时满足第 5 级门槛时直接升到 5,不逐级停留。
3. 停用的等级**不能升入**,判定时跳过它继续比对更高的启用等级。
4. 保级周期起点:玩家升入一个新等级的时刻就是该等级第一个保级周期的起点;周期长度为一个完整日历月。例:9 月 12 日 15:00 升级,首次结算为 10 月 12 日 15:00。
5. 月末日期处理:下一月没有同一日期时取该月最后一天,时刻不变。例:1 月 31 日 15:00 升级,首次结算为 2 月最后一天 15:00;后续周期以上一次结算时刻为起点。
6. 周期到期:取该玩家在本周期内的有效投注与所在等级的保级流水比对。达成则保持等级并紧接着开始下一个完整日历月;未达成则降到「未完成降级」填写的等级(A12),并从降级时刻开始目标等级的完整日历月。该格留空则保持等级并开始下一周期。
7. 周期内再次升级:旧等级的保级周期立即结束,以本次升级时刻为新等级的周期起点,重新给予一个完整日历月。
8. 降级目标若在此期间被归档或停用,本次**不降级**并告警提示运营补配。
9. 每次升降级与保级结算都写流水:周期起止时间、前后等级序号、触发原因、判定时的累计充值、累计有效投注与周期有效投注。
10. 活动开关关闭时(A1)不做任何判定,玩家等级停在原地。

**错误处理**

| 错误状况 | 提示 |
|---|---|
| 玩家当前等级已归档 | 不应发生;拦下判定并告警,要求修复迁移数据 |
| 降级目标已归档或停用 | 本次不降级,告警提示补配降级目标 |
| 有效投注取数失败 | 本次不判定、不按 0 顶替,下个周期重试;与 M2-D34「取数失败判否」同口径 |
| 判定过程中等级配置被改 | 按判定开始那一刻读到的配置走完,不中途换规则 |

**测试案例**

- 正向:玩家 9 月 12 日 15:00 升到 VIP3,保级流水为 3000 → 10 月 12 日 15:00 检查这一个完整周期;完成 3500 则保级成功,下一次结算为 11 月 12 日 15:00。
- 逆向:玩家累计充值 2000 但累计有效投注只有 100,VIP2 门槛为 500 / 1000 → **不升级**;玩家周期有效投注为 0、所在等级保级流水 1000、降级目标填 VIP1 → 到期降到 VIP1 并留痕。

### 4.6-R5

**触发条件**:玩家在对应的领取窗口内点领取(玩家端动作)。无后台按钮。

**可输入数据**:无人工输入;发放金额由玩家当时的等级与三张奖励表推出。

**功能范围**

| 归属 | 做什么 |
|---|---|
| 界面 | 无。发放结果在「VIP 奖励发放记录」里看 |
| 服务端 | 窗口校验、资格校验、金额计算、彩金入账、建打码任务、写发放记录 |

**处理逻辑**

1. 查窗口:当前时刻是否落在该类奖励的领取窗口内(A6 / A7 / A8),按业务时区判;不在窗口内拒绝。
2. 查资格:活动开着(A1);玩家命中全部选中标签(A3);未被封禁。注册渠道若有限定,已经包含在用户标签的「渠道来源」属性条件中(A4),本页不再单独判断。
3. 查等级:取**领取那一刻**的等级(A20);等级已归档则不发并告警。停用等级中的原有玩家在迁移前仍按该级配置领取。
4. 算金额:周 / 月奖励取该级配的固定金额;投注返现取上一自然日有效投注 × 该级返现比例(A18)。
5. 取本月累计充值:三类奖励统一取领取所在自然月 1 日 00:00 至领取时的成功到账充值。时间按业务时区,金额按标准计价币种累计。
6. 判门槛:本月累计充值达到该类奖励的全额门槛 → 发基础奖励的 100%;未达到(含 0 充值)→ 只能发「基础奖励 × 免费领取百分比」;免费比例为 0% 时不发(A15)。
7. 免费部分领完即占用本期领取名额。玩家随后充值达到全额门槛,本期也不补差额、不允许再次领取。
8. 发放:以彩金入账,带「VIP 奖励」来源标识,按 A5 的倍数**独立建一条打码任务**(M2-D3);本模块不直接改余额。
9. 留痕:写一条发放记录 —— 玩家、奖励类型、发放当时的等级序号、基础奖励、月累计充值、全额门槛、实际发放比例、实际金额与币种、打码倍数、触发的账变、时间。
10. 同一期同一类奖励**每人只能领一次**;并发点击只成功一次。

**错误处理**

| 错误状况 | 提示 |
|---|---|
| 不在领取窗口内 | 按服务端时间判定,拒绝;不以玩家端时间为准 |
| 本期已领过 | 拒绝,不重复发放、不重复建打码任务 |
| 本月累计充值未达到全额门槛 | 按免费比例发;比例为 0% 时在玩家侧呈现「不可领取」 |
| 玩家所在等级已归档 | 不应发生;不发放并告警,要求修复迁移数据 |
| 入账失败 | 不记发放、不占用本期名额,玩家可重试;与 4.2-E8 同口径 |
| 换算失败(标准币金额待补算) | 本次不发、事后不补发;与 4.4-A24、`标准计价.md` S7 同口径 |

**测试案例**

- 正向:VIP3 玩家领 50 的周奖励,本月累计充值门槛为 100、免费比例为 20%。本月累计充值 80 → 发 10 彩金并占用本期名额;本月累计充值 100 → 发 50 彩金。两者都按 3 倍为实际发放额建立打码任务。
- 逆向:玩家先领了 10 的免费部分,当天稍后充值达到 100 → 不补另外 40;同一分钟连点三次也只成功一次;窗口关闭后再领 → 拒绝且不补领(A21)。

### 4.6-R7

**触发条件**:玩家提交出款申请。没有本页后台按钮;M5 出款申请接口在正式受理前调用本规则。

**可输入数据**:玩家提交的出款币种与申请金额。VIP 等级、等级上限、业务日期和标准币金额均由服务端取得,不接受玩家端传值作为判定依据。

**功能范围**

| 归属 | 做什么 |
|---|---|
| VIP 配置(M4) | 拥有每个等级的当日最高出款次数与最高出款金额,向 M5 提供当前启用配置 |
| 出款链路(M5) | 在受理申请前读取 VIP 等级与上限,换算标准币金额,原子校验并占用额度,随订单状态转为已使用或释放 |
| 玩家端(范围外) | 展示当天剩余次数、剩余金额和被拒原因;不得自行计算后替代服务端判定 |

**处理逻辑**

1. 定业务日:按平台业务时区确定申请所属自然日,统计区间为当日 00:00:00 至次日 00:00:00。
2. 取规则:读取玩家在申请到达服务端那一刻的 VIP 等级,再读取该等级最新的「当日最高出款次数 / 金额」。VIP 活动开关关闭时仍执行本规则(A1)。
3. 换算金额:以本单申请金额(手续费前总额)按申请时刻汇率换算成平台标准计价币种并固化在订单上;不是按预计到账净额统计。换算未就绪或失败时拒绝受理,不得按 0 计算。
4. 算已用额度:汇总该玩家同一业务日内所有**放款成功**和仍处于**待审核 / 审核中 / 放款中**的申请。每笔计 1 次,金额取各单申请时固化的标准币金额。
5. 同时校验:
   - 已用次数 + 1 ≤ 当前等级当日最高出款次数;
   - 已用金额 + 本单标准币金额 ≤ 当前等级当日最高出款金额。
   两项都满足才能受理;任一不满足就整单拒绝。
6. 原子占用:并发请求必须在同一事务或等价的原子机制中完成“读取已用额度 → 校验 → 占用”。不能先查后异步写,否则两笔都可能看到旧余额并同时通过。
7. 状态结转:申请被受理即占用次数与金额;放款成功后占用转为已使用。审核拒绝、玩家取消、通道明确失败时,只有在资金占用已解除或归位后才释放本日额度。回执超时或结果未知继续占用,不得猜测失败。
8. 跨日订单:额度永远归申请受理时的业务日。次日才放款成功不占次日额度;旧日订单次日失败释放时,只修正旧日记录,不增加次日额度。
9. 等级或配置变化:已受理及已成功订单不撤销。玩家再次申请时按最新等级与配置重新计算,但本日既有成功和占用仍全部计入。例如 VIP1 已用 1 次 / 20 USD,升到上限 3 次 / 100 USD 的 VIP2 后,当天剩余 2 次 / 80 USD。
10. 留痕:订单保存申请时 VIP 等级序号、次数上限、金额上限、本单标准币金额、判定前已用次数 / 金额、判定结果与业务日期,保证事后能解释为何放行或拒绝。

**错误处理**

| 错误状况 | 处理与提示 |
|---|---|
| 已达到次数上限 | 今日出款次数已达 VIPX 上限 N 次,明日可再次申请 |
| 本单会突破金额上限 | 今日剩余可出款金额为 X USD,本次申请超过 VIPX 每日限额 |
| 次数或金额上限为 0 | 当前 VIP 等级今日不可出款 |
| 玩家 VIP 等级或等级配置缺失 | 安全拒绝,不按无限额放行;告警运营补齐配置 |
| 标准币换算失败或待补算 | 本次不受理、不占额度;提示稍后重试并告警 |
| 并发申请 | 只允许不突破上限的请求成功占用;其余返回最新剩余额度 |
| 通道结果未知 | 继续占用,等待回执或对账;不提前释放 |

**测试案例**

- 正向:VIP1 当日上限 1 次 / 20 USD,当日尚未出款,申请 20 USD → 受理并占用 1 次 / 20 USD;再次申请 1 USD → 因次数与金额均无剩余被拒。
- 正向:VIP2 当日上限 3 次 / 100 USD,已成功 20 USD、另有放款中 30 USD → 剩余 1 次 / 50 USD;申请 50 USD 通过,申请 50.01 USD 被拒。
- 正向:一笔 20 USD 申请被审核拒绝且资金已解除占用 → 当日次数和金额释放,玩家可再次申请。
- 逆向:VIP1 上限 1 次 / 20 USD,两笔 15 USD 并发到达 → 最多一笔成功占用,不能两笔都通过。
- 逆向:玩家已经使用 1 次 / 20 USD 后被降到上限 1 次 / 10 USD 的等级 → 已成功出款不追回,剩余次数与金额均按 0 展示,当天不得再申请。

## 8. 数据流向与系统串接

**数据流向**:运营填三个区块 → 服务端整份校验后存成配置 → 玩家充值 / 投注触发升级判定、
个人保级周期到期触发保级与降级判定 → 玩家在窗口内领取,服务端按月累计充值判断发全额或免费部分、通知加钱记打码、写发放记录 →
玩家申请出款时 M5 读取当时等级与逐级上限、原子占用或拒绝 → 本页读出配置显示,4.7 读出奖励发放记录显示。

**系统串接**:

- 钱包和账变、打码任务(归财务):加彩金和记打码都走财务那边,带「VIP 奖励」来源标识;
  这里只触发,不自己改余额。资金域不在账务链路上反向依赖本活动。
- 有效投注(归玩法,**本仓库范围外**):升级门槛的投注项、保级流水、投注返现的基数都用它;
  口径为实际投注 × 游戏折算比例,与提现流水、打码、代理返佣同口径(A11)。
- 玩家充值汇总(归财务):升级门槛的充值项、各类奖励的月累计充值门槛判定都用它。
- 用户标签(归 M2,2.5):活动绑定的标签,领取时按当下命中集判断;
  注册渠道也由标签的「渠道来源」属性条件表达;**标签只用于领取门槛,不参与等级判定**(铁律④第 2 款)。
- 渠道(归代理渠道,**本仓库范围外**):2.5 用户标签只读它的渠道字典与玩家注册渠道;VIP 本页不直接读取。
- 标准计价换算(归财务):升级门槛与月累计充值门槛的判定用标准币金额。
- 出款订单与额度占用(归财务):M5 在申请受理前只读玩家 VIP 等级和本页的逐级出款上限,固化判定快照并拥有额度占用、释放与订单状态;M4 不写订单。
- **除了平台自己的钱包 / 标签 / 充值投注数据,没有别的外部系统;渠道数据由 2.5 用户标签封装后提供。**

## 9. 异常与边界

| # | 场景 | 触发条件 | 预期处理 |
|---|---|---|---|
| E1 | 越权 | 没权限的账号改配置 / 切开关 | 服务端拦下,不靠藏按钮 |
| E2 | 同一人连点领取 | 同一玩家同一期并发点领取 | 只成功一次,只加一次钱、只建一条打码任务 |
| E3 | 窗口边界 | 玩家点击到达服务端时窗口刚关 | 按服务端时间判定,拒绝;不以玩家端时间为准 |
| E4 | 领取途中升降级 | 玩家在窗口内升级后再领 | 以点领取那一刻的等级为准(A20);已领的不回溯、不补差 |
| E5 | 领取途中标签变化 | 玩家在窗口内被打上或摘掉参与标签 | 以点领取那一刻的命中集为准,不回溯已领的 |
| E6 | 等级停用后仍有玩家 | 运营停用某级,该级还有玩家 | 允许停用;新玩家不能升入,原玩家在迁移前保持该级并继续按该级领奖。运营选择已启用的更低等级批量迁移,清空后才能归档(D60) |
| E7 | 降级目标缺失 | 「未完成降级」指向的等级被归档或停用 | 本次不降级,告警提示补配(R4 第 8 步) |
| E8 | 月奖励窗口落在小月 | 配了 31 号,当月只有 30 天 | 顺延到该月最后一天开窗(A19) |
| E9 | 周期跨月的返现 | 返现窗口配在 00:00 ~ 01:00,跨了自然日 | 领的始终是上一自然日的有效投注,按业务时区切,不因窗口跨点而改基数 |
| E10 | 活动进行中关开关 | 运营在窗口内关掉活动 | 立刻停止 VIP 升降级判定与 VIP 奖励发放,已发的不收回;每日出款上限继续执行(A1) |
| E11 | 改配置影响未领奖励 | 运营在窗口内改了某级的奖励金额 | 保存即生效,**尚未领取的按新值发** —— A20 的快照锁的是"已发放的",不是"未领取的" |
| E12 | 等级序列改动波及红包雨 | 新增或停用等级后 4.2 的金额档出现缺口 | 本页保存不拦,但给提示;真正的拦截在 4.2 保存时(4.2-A6) |
| E13 | 有效投注取数失败 | 玩法侧数据未就绪 | 不判定、不按 0 顶替,下个周期重试(M2-D34 同口径) |
| E14 | 先领免费部分后充值达标 | 玩家本期已按免费比例领取,之后月累计充值达到全额门槛 | 不补差额、不允许再次领取;发放记录保留领取时的累计充值、门槛和实际比例 |
| E15 | 并发出款撞额度 | 玩家同时提交多笔,单笔都未超但合计会超 | 原子校验与占用,只放行仍在次数和金额上限内的申请;其余返回最新剩余额度 |
| E16 | 出款途中升降级或改配置 | 申请已受理后等级或上限变化 | 不撤销已受理申请;下一笔按最新等级与配置判断,本日既有成功与占用继续累计(A24) |
| E17 | 出款失败释放额度 | 审核拒绝、取消或通道明确失败 | 资金占用解除或归位后才释放该申请日的次数和金额;结果未知继续占用 |
| E18 | 跨币种出款 | 玩家使用非标准计价币种申请 | 按申请时刻汇率固化标准币金额后判定;换算失败则不受理、不占额度 |
| E19 | VIP 配置缺失 | 玩家没有合法等级或等级没有两项出款上限 | 安全拒绝并告警,不得按无限额放行 |

## 10. 状态清单

| 状态 | 表现 |
|---|---|
| 错误 | 保存失败在页面顶部报错并把错误行标红,能改了再存;不整页崩 |
| 已关闭 | 活动开关关着时,页面顶部标「已关闭」,配置仍可改 |
| 等级已停用 | 该行整行置灰,状态列显示「停用」并展示待迁移玩家数;仍可编辑、展开奖励表与发起迁移 |
| 等级已归档 | 不在日常等级表与升级候选中显示;历史查询仍按永久保留的序号与名称展示 |
| 免费比例为 0% | 明确提示「本月充值未达标时不可领取」,避免运营误以为系统会另发免费部分 |

| 奖励区未展开 | 等级表默认收起奖励区,只显示等级行;展开后在行下方铺开三张表 |
| 序号有空洞 | 等级序号不连续时正常显示,不补位、不重排,不做任何提示 |
